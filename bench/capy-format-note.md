# Capycap-AI/CaptchaSolve30k schema caution

Dataset: https://huggingface.co/datasets/Capycap-AI/CaptchaSolve30k (Apache-2.0 with dataset-card usage restrictions). The published card says `inputStream` stores 9-byte samples: float32 x, float32 y, one button byte. In the first 20 rows of the public test split, decoded byte length was **exactly 4 × `inputSampleCount`** for the sampled rows inspected, not 9 ×. A naive nine-byte decode produces nonsense and must not be used. The project's replay demo uses `tickInputs`, not `inputStream`. The first 20 test rows include 15 mouse and 5 touchscreen rows. Using changing `tickInputs` states at 240Hz yields 0/15 mouse rows flagged by the current rule; this is only an exploratory game-input diagnostic, not a browser false-positive estimate. No raw examples are included in this repo.

Expanded test: downloaded the full 5,000-row test split locally (not redistributed). All first 60 rows inspected have decoded `inputStream` byte count exactly 4 × `inputSampleCount`, and the demo replay at https://huggingface.co/spaces/Capycap-AI/CaptchaSolve-Demo uses `tickInputs` rather than this binary stream. For the motor-control stress test, 4,397 mouse and 603 touch rows yielded 170/5,000 behavior-only `likely-automated` flags before the safety change, 0 after demoting those flags to `review`. Game physics ticks are not DOM pointer events, and no browser FPR follows.
